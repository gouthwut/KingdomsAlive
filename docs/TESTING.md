# Проверки

## M0

1. Выполни `rustfmt --check mixins/kingdoms_alive/server_start_smoke.rs`.
2. Собери мод лаунчером по [README](../README.md). В `%APPDATA%/horizon-launcher/native/build.log` ищи успешное применение одного mixin и завершение Cargo.
3. Открой `KA-M0-Smoke` в профиле `kingdoms-alive-m0`. Проверь, что загружен мир и в журнале есть `[kingdoms_alive] M0 server_about_to_start dedicated=false`. Журнал профиля находится в `%APPDATA%/horizon/instances/kingdoms-alive-m0/logs/latest.log`. При автоматизированном запуске через `horizon-ctl` также проверь журнал рядом с адресом управления.
4. Вместо ручного запуска можно выполнить `python tools/smoke_m0.py`. Скрипт требует включённого Horizon MCP и тестового профиля со сборкой. Он ждёт появления игрока и загрузки чанков, ищет маркер в журнале и сохраняет `result.json` и `world.png` в `target/m0-smoke/`. По окончании скрипт закрывает игру с сохранением. Для независимой проверки пакета используй `cargo horizon-mod check target/kingdoms_alive-0.1.0.hnmod --json`.

## M1

Запусти `cargo test --locked`, `cargo fmt --all --check` и `cargo clippy --locked --all-targets -- -D warnings`. Тесты ядра сверяют границы, приоритет, повторное чтение и отказ перезаписать повреждённый или более новый файл.

1. Собери пакет в отдельном профиле `kingdoms-alive-m1` на Nightly из [README](../README.md). В отдельном творческом мире найди существующую деревню, перейди туда и закрой мир с сохранением.
2. В каталоге этого мира рядом с `level.dat` создай `kingdoms_alive_register.json` в UTF-8. Пример для тестовой равнинной деревни, координаты следует заменить для другого мира.

   ```json
   {
     "name": "Plains Village",
     "territory": {
       "dimension": "minecraft:overworld",
       "center": [272, 68, 944],
       "radius": 64
     },
     "housing_capacity": 0
   }
   ```

3. Открой мир и дождись загрузки деревни. Граница представляет собой квадрат по X/Z с радиусом от 1 до 128 блоков. Когда чанки участка загружены и в нём тикает хотя бы один обычный житель, мод запишет `kingdoms_alive.json` со схемой 1 и пустым складом. Сверь в журнале `M1 registered` и строку `M1 tick=` с приоритетом `Food`. Скопируй снимок для проверки.
4. Закрой игру с сохранением и открой тот же мир, оставив заявку на месте. Проверь `M1 loaded`, повторный расчёт приоритета и точное совпадение снимка. В M1 ненулевые остатки проверялись подстановкой в копию снимка. Начиная с реестра M2b эти числа исторические: проверяй ненулевые запасы через физические сундуки по разделу ниже.
5. В закрытом тестовом мире сохрани копию исправного снимка и запиши заведомо повреждённый JSON на его место. При открытии и закрытии мира проверь `M1 open refused` и точное совпадение повреждённого файла. Верни исправную копию.

Проверку можно провести через Horizon MCP с `play`, `game_wait_ready` и `game_quit`. Путь к журналу аналогичен M0, с именем профиля M1.

## Пилот M2

1. Собери мод лаунчером в отдельном профиле `kingdoms-alive-m2`. Сделай копию тестового мира с зарегистрированной деревней. На безопасной ровной площадке в её границах поставь одиночный сундук и назначь ему уникальное имя. В текущей ревизии для стенда подходит команда `/data merge block 284 90 947 {CustomName:'"KA-M2 warehouse"'}`.
2. Проверь состояние блока через MCP `game_block`. В закрытом тестовом мире добавь рядом с `level.dat` файл `kingdoms_alive_delivery.json`. Пример для стенда. UUID указывается десятичным числом из снимка M1. `approach` — доступное место рядом с сундуком на той же высоте. `chest_name` — сырое строковое значение `CustomName` из NBT.

   ```json
   {
     "resident": 47337932765279898664837487559844216321,
     "chest": [284, 90, 947],
     "approach": [283, 90, 947],
     "chest_state": "minecraft:chest[facing=north,type=single,waterlogged=false]",
     "chest_name": "\"KA-M2 warehouse\""
   }
   ```

3. Открой мир. Поставь выбранного жителя на той же площадке в нескольких блоках от сундука и через `/item replace entity <UUID> weapon.offhand with minecraft:oak_log 1` выдай ему одно бревно. Сверь `M2 navigation` и `M2 delivered` в журнале. Открой сундук и проверь один предмет в его слотах и пустую вторую руку жителя.
4. Закрой игру с сохранением и открой тот же мир. Сверь сундук, руку и сообщение `M2 claim exists`. Запрос остаётся рядом с миром. Файл `kingdoms_alive_delivery.claim` означает, что операция могла начать менять физическое состояние. Для нового прогона используй чистую копию стенда.
5. Для отдельного прогона заполни все 27 слотов булыжником. Выдай жителю бревно и проверь, что рука сохранилась и файл попытки отсутствует. Освободи слот и проверь доставку. Для проверки конфликтов замени утверждённый сундук до выдачи груза и проверь отказ. Обычное разрушение после доставки проверяется по выпавшему предмету и отсутствию повторной вставки.
6. Для отзыва разрешения сначала убедись, что задача активна: нет `M2 approved chest unavailable`, отказа запроса или тайм-аута. Удали либо измени файл запроса, пока игра открыта. Через 5 серверных тиков ожидается `M2 approval revoked`, нет claim, груз остаётся в руке и освобождение слота больше не запускает доставку. Новый запрос применяется только при повторном открытии мира.

Пилот не является аварийно-атомарным: он синхронно сохраняет удаление из руки перед вставкой, а сундук сохраняется отдельно. Использовать только в одноразовой копии мира. Для повторяемого лесоруба нужны проверки из [протокола восстановления](M2_RECOVERY.md), а не удаление claim.

На Windows после `game_quit` дождись завершения процесса и освобождения runtime lock. После `play` сначала дождись регистрации сокета управления, затем загруженного игрока. Не удаляй блокировки и не перезапускай вслепую ещё один клиент.

## Реестр склада M2b

Рядом с `level.dat` зарегистрированного тестового мира создай `kingdoms_alive_warehouses.json`. Это разрешение на **чтение**, не на добычу или перенос. Пример для существующего стенда:

```json
{
  "schema": 1,
  "settlement": 1,
  "dimension": "minecraft:overworld",
  "chests": [
    {
      "pos": [284, 90, 947],
      "state": "minecraft:chest[facing=north,type=single,waterlogged=false]",
      "name": "\"KA-M2 warehouse\""
    }
  ]
}
```

ID должен совпадать со снимком поселения, сундук должен быть в его границе. Максимум восемь одиночных сундуков, повтор координат запрещён. Метка — сырое значение `CustomName`, состояние должно совпадать точно. Двойные сундуки и контейнеры с `LootTable` не поддержаны. Реестр перечитывается раз в 20 серверных тиков; недоступность хотя бы одного сундука делает весь остаток неизвестным и останавливает вычисление нужды. Отсутствующий с открытия мира реестр означает нулевые утверждённые запасы, не восстановление чисел M1. Снимок M1 остаётся историческим и не переписывается.

1. Проверь `M2 physical stock=Some(...)` на пустом сундуке. Добавь 12 брёвен, 4 хлеба и 6 булыжника: ожидаются дерево 12, еда 4 и камень 6. Изъятие 11 брёвен должно уменьшить дерево до 1.
2. Измени метку сундука либо отзови реестр во время игры: ожидается `M2 physical stock=None`. Верни явное разрешение и метку, проверь повторное чтение реальных слотов. Имя — ограниченная проверка идентичности, не криптографический ID: замена с тем же состоянием и скопированным именем неотличима и для будущих операций записи требует более сильного протокола.
3. Закрой и снова открой мир. В наблюдении должны остаться реальные 4/1/6, даже если исторические счётчики снимка завышены. Снимок не должен измениться. Никакие предметы не создаются из счётчиков.

На текущей сборке в игре проверены один и два сундука, отказ при дубликате координат и повреждённом JSON, разрушение второго сундука с переходом к неизвестному остатку, затем явное удаление его записи из реестра. Повреждённый JSON мод не перезаписывает. Выгрузка чанков ещё требует игрового прогона; ограничение восьми сундуков проверено в ядре. Реестр пока не управляет отдельным пилотом доставки. Перезапуск и отзыв реестра не доказывают аварийно-безопасный перенос.

## Опытный лесоруб

**Только одноразовая копия мира.** Цикл работает в нормальном сеансе, но журнал ещё не восстанавливает предметы после аварии. Сохранения источника, руки и сундука раздельные; остановка неопределённой операции запрещает повтор, но не исключает потерю. Не удаляй журнал, claim или временный файл ради продолжения.

1. Зарегистрируй жителя и одиночные сундуки через реестр выше. Без запроса лесоруба реестр сам не добывает и не переносит. При явном запросе ниже сундуки реестра становятся назначенными местами доставки. Используй свободную ровную площадку внутри территории, с доступным западным подходом к источникам и сундуку.
2. В новой копии не должно быть запроса или claim старого пилота доставки. Они блокируют лесоруба; файлы запроса, журнала и временного журнала лесоруба, в свою очередь, блокируют старый пилот. Не используй мир с неопределённой старой операцией как новый стенд.
3. Поставь два настоящих `minecraft:oak_log[axis=y]`, например `[278,90,947]` и `[280,90,947]`, проверь воздух западнее и над точками подхода. У жителя должна быть пустая вторая рука. **Не выдавай бревно в руку.** Закрой мир и рядом с `level.dat` запиши `kingdoms_alive_lumberjack.json`:

```json
{
  "job": "oak-test-1",
  "resident": 47337932765279898664837487559844216321,
  "min": [278, 90, 947],
  "max": [280, 90, 947]
}
```

UUID и координаты относятся к нашему стенду; в другом мире их нужно заменить. `job` — непустая строка до 64 байт, зона не больше 8×4×8 и целиком в территории. Разрешение явно допускает добычу дубовых брёвен в этой зоне, включая поставленные игроком. Это не поиск естественных деревьев. Запрос читается при открытии, изменение или удаление на работающем сервере останавливает задачу; вернуть запрос недостаточно для возобновления в том же сеансе.

4. Открой мир. Ожидай `M2 lumberjack harvested`, затем `M2 lumberjack delivered`. Два исходных блока должны исчезнуть, в сундуке должны быть ровно два бревна, рука — пустая. В `kingdoms_alive_lumberjack_journal.json` две операции должны иметь `Delivered`. После обычного перезапуска предметы остаются, повторная установка бревна по использованному адресу не разрешает его добыть снова в этом запросе.
5. В отдельной копии заполни все сундуки до начала: источник и пустая рука не меняются, журнал не появляется. Освободи слот, дождись `Carrying`, снова заполни склад: груз остаётся в руке. Разрушение сундука или отзыв разрешения не создают замену склада или компенсационный предмет. При открытии с любым незавершённым состоянием ожидается `interrupted operation held; no replay`. Требуется ручная сверка физических объектов; автоматического продолжения нет.

Подтверждение прогона текущей реализации: `target/m2-smoke/lumberjack.json`, сборка `native-fdc87ae-acd650484d83`, `ok: true`. Изменённый хуком лут, выгрузка чанка и аварийные записи в этом прогоне не проверялись. Лут, отличный от одного стандартного дубового бревна, после подтверждённого удаления блока выбрасывается на месте и задача удерживается. При ошибке удаления блока мод не создаёт ни груз, ни выпавшую копию.

Ограничения: только западная точка подхода к источнику, тайм-аут пути 400 тиков, без выбора альтернативного источника при недоступном первом, одна задача на мир и один житель, без инструментов и времени рубки. Каждая операция вызывает синхронное сохранение уровня и сущностей; нагрузочный бюджет ещё не измерен. Неизвестные остатки других складов приостанавливают планирование нужд, но лесоруб может доставлять в отдельный доступный утверждённый сундук. Это опытный цикл, не завершение M2c.

## Дальнейшие игровые этапы

- Модульные тесты проверяют границы остатков, резервирование, возврат груза, приоритеты и повторную сдачу заказа.
- Интеграционные тесты проверяют полный оборот ресурса, возобновление строительства, сохранение и миграции. Для ошибок записи проверяй предыдущий снимок и повтор операции.
- В игре наблюдай живых NPC, блоки, инвентарь и реальное сохранение с перезапуском. Для конфликтов измени блок между назначением задания и применением, затем сравни состояние и остатки.
- В M6 измеряй для 1, 5, 10 и 25 поселений длительность серверных тиков (p50, p95, p99), память, время записи, FPS и глубину очередей. Используй один мир и одинаковые настройки, запиши длительность и параметры прогонов.
